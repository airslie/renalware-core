# Mirth statistics monitoring

## Purpose

We want administrators to see whether Mirth channels are healthy, particularly whether queues or
errors are building up. We also want to support alerting without making Renalware, or a future
application such as App X, the long-term owner of infrastructure monitoring.

Channel statistics are operational data and must not contain patient data.

## Current approach

A scheduled Mirth channel collects statistics from its own Mirth instance and sends a JSON snapshot
to Renalware.

```text
Mirth JavaScript Reader
  -> Mirth in-process controller APIs
  -> JSON statistics report
  -> HTTP Sender with scoped bearer token
  -> Renalware statistics API
  -> statistics tables and Renalware admin dashboard
```

The example channel is in [example_poll_stats_channel.xml](example_poll_stats_channel.xml). It uses
Mirth's in-process `ControllerFactory` APIs rather than authenticating to the Mirth User API. This
avoids giving Renalware a highly privileged Mirth username and password and works in both container
and Windows VM deployments without another executable or service.

The channel sends cumulative received, sent, error and filtered counts, the current queued count,
and the channel state. Every report includes:

- a unique `report_id`, used to make retries idempotent;
- `reported_at`, generated by the Mirth instance;
- stable `site_id` and `instance_id` values;
- Mirth's `server_id`, when available; and
- a versioned payload (`schema_version`).

The Renalware endpoint is:

```text
POST /api/v1/monitoring/mirth/channel_stats
Authorization: Bearer <token>
```

It accepts only a scoped API credential with `mirth_statistics:write`. Credential issuance and the complete payload are
documented in [API credentials](../api_credentials.md#mirth-channel-statistics).

Endpoint URLs, bearer tokens, and site identifiers should be held in Mirth's Configuration Map,
not embedded in an exported channel. Use verified HTTPS outside local development and avoid logging
the authorization header or complete request configuration.

For a push-based deployment, configure Renalware with:

```text
MONITORING_MIRTH_ENABLED=true
MONITORING_MIRTH_POLLING_ENABLED=false
```

The first setting displays the dashboard. The second disables the old GoodJob task that signs in to
the Mirth User API and pulls statistics. Existing deployments retain the old polling behaviour when
`MONITORING_MIRTH_POLLING_ENABLED` is not set.

## Why this is the pragmatic first step

- It removes the need for a privileged Mirth User API credential in Renalware.
- Mirth makes an outbound HTTPS request, which is usually easier to permit through site firewalls.
- It works wherever Mirth runs, including Windows VMs where we do not currently deploy sidecars.
- It reuses Renalware's existing database and admin UI, so it has a small deployment footprint.
- The versioned JSON contract creates a boundary that can later be moved out of Renalware.

The main compromise is that some monitoring code lives in Mirth JavaScript and uses Mirth internal
Java APIs. The example channel must therefore be tested when Mirth is upgraded. More importantly,
Mirth cannot report that it is completely unavailable. The receiver or alerting platform must alert
when reports stop arriving; this freshness check is as important as queue thresholds.

## Moving ingestion out of Renalware

The preferred long-term ownership is a small, application-neutral observability service. It would
receive reports from Mirth instances, retain or forward the data, expose metrics, and own alert
configuration. Renalware and App X would not need privileged access to Mirth and would not duplicate
collection code.

The current endpoint is intentionally suitable for extraction. A future service should initially
preserve:

- the version 1 JSON contract and idempotent `report_id` behaviour;
- the `site_id`, `instance_id`, `server_id`, and channel identifiers;
- scoped, independently revocable credentials for each site and Mirth instance; and
- the accepted, duplicate, invalid, and unauthorized response semantics.

This service could be a small Ruby web application if that best matches our support skills. It does
not have to be deployed beside Mirth: it only needs an HTTPS endpoint reachable from each Mirth
instance. In Azure it could run in an existing shared application platform initially, or in a
dedicated App Service, Container App, or Function if provisioning becomes available. The hosting
choice is less important than keeping the ingestion contract independent of Renalware concepts.

A low-risk migration would be:

1. Deploy the neutral endpoint with the same payload contract.
2. Test it with a non-production Mirth instance or a second HTTP Sender destination.
3. Change each Mirth instance's configured endpoint and credential.
4. Verify report freshness and counts in the new store.
5. Make Renalware read a small status API or metrics source, if an in-application summary is still
   useful.
6. Retire Renalware ingestion after all sites have moved.

Historical backfill is probably unnecessary for queue monitoring. If it becomes valuable, the
report and channel statistics tables provide a clear export source.

## Prometheus, Grafana, and Azure

Prometheus and Grafana should be treated as presentation and alerting infrastructure, not as a
requirement for collecting the first statistics report. The current database-backed receiver lets
us add them later without changing the Mirth channel.

When OpenTelemetry is enabled, the Renalware receiver emits OTLP metrics for each accepted Mirth
statistics report. These can be collected by the Azure OpenTelemetry sidecar and forwarded to
Application Insights/Azure Monitor for dashboards and alert rules. The emitted metrics are:

```text
mirth_channel_queued
mirth_channel_received_total
mirth_channel_sent_total
mirth_channel_error_total
mirth_channel_filtered_total
mirth_stats_last_report_timestamp_seconds
mirth_channel_state
```

Attributes are limited to stable, bounded identifiers: `site_id`, `instance_id`, `server_id`,
`channel_id`, and `channel_name`. Never use `report_id`, timestamps, errors, or other unbounded
values as metric attributes. No patient identifiers should appear in metric names, attributes,
dashboards, or logs.

Received, sent, error, and filtered values are cumulative counters and may reset when a channel is
reset, redeployed, or recreated. Queue depth is a gauge. `mirth_channel_state` is `1` when the
channel state is `Started` and `0` otherwise. Alert queries must account for counter resets and
should use changes over a time window rather than treating cumulative totals as recent activity.

Azure dashboards can then use the Application Insights/Azure Monitor custom metrics. A
Prometheus-compatible `/metrics` endpoint remains a possible future addition for sites that operate
Prometheus/Grafana, but Mirth's JSON contract does not need to change.

Renalware and App X may still show a compact, read-only operational summary, such as current queue
depth, last report time, and overall status. Alert rules, acknowledgement, notification routing, and
detailed investigation dashboards should remain in the shared observability platform. The
applications can link to the relevant Grafana dashboard rather than recreating it.

## Suggested alerts

Alerting should cover absence and rate-of-change conditions, not only absolute queue size:

- no report received from an expected instance for a defined period;
- channel state is not `STARTED` outside a maintenance window;
- queued count exceeds a per-channel threshold for a sustained period;
- queued count continues to rise over a sustained period;
- error count increases above a threshold or error rate;
- no received or sent activity where a channel is expected to be active; and
- the receiver itself is unavailable or rejecting reports.

Thresholds will differ between channels. A short-lived queue can be normal, while a queue of one may
be important for a low-volume channel. Alert configuration should therefore support per-channel
overrides, duration conditions, maintenance suppression, and notification routing.

## Operational considerations

- **Sampling interval:** Choose an interval that detects incidents promptly without producing
  unnecessary storage. One to five minutes is likely sufficient; the example channel's shorter
  interval is useful for local testing.
- **Delivery failure:** A missing snapshot is normally repaired by the next snapshot because the
  report contains current cumulative counts and queue depth. Short retries are safe because report
  IDs are idempotent. Avoid an unbounded destination queue inside the system being monitored.
- **Freshness:** Track receiver arrival time as well as Mirth's `reported_at`. Alert on missing
  reports and monitor clock skew; a badly incorrect future timestamp must not hide later data.
- **Retention:** Define retention or downsampling before the number of sites and channels grows.
  Recent high-resolution data and longer-lived hourly or daily aggregates may be sufficient.
- **Channel identity:** Use Mirth's channel UUID as the stable identity. Names are display labels and
  can change.
- **Credential management:** Use one narrowly scoped credential per site or instance. Store only in
  an appropriate secret/configuration store, rotate it, and revoke it when an instance is retired.
- **Transport:** Use verified TLS. Network restrictions should permit only the required outbound
  path where practical.
- **Upgrades:** Test the statistics channel against each supported Mirth release because it uses
  internal Java controller APIs.
- **Monitoring coverage:** Channel counts do not cover Mirth process health, JVM memory, disk space,
  database health, host availability, certificate expiry, or network connectivity. Collect those
  separately through the site's normal Azure Monitor, VM, container, or infrastructure agents.

## Other collection patterns

An external exporter remains a valid future alternative. It could run as another container next to
containerised Mirth, as a Windows service on VM installations, or centrally where network access is
available. It would poll Mirth and expose Prometheus or OpenTelemetry metrics. This becomes more
attractive if Mirth gains suitably restricted API credentials and consistently verified TLS.

At present it adds another runtime to deploy and still requires a highly privileged Mirth API
credential, so it is not preferred over the scheduled channel. Similarly, duplicating the current
Renalware poller in App X would reproduce both the credential risk and monitoring logic and should
be avoided.

## Direction

The intended progression is:

1. Use the scheduled Mirth channel and Renalware endpoint now.
2. Add freshness and queue visibility in Renalware where it helps current administrators.
3. Extract the receiver when App X or multi-application ownership makes a neutral service valuable.
4. Expose Prometheus or OpenTelemetry metrics from that receiver.
5. Put detailed dashboards, alert rules, and notification routing in Grafana/Azure observability.
6. Keep only concise status summaries and links in Renalware and App X.

This sequence solves the immediate security and deployment problem without committing the final
monitoring architecture to Renalware.
